## **프로젝트 코딩 컨벤션 및 가이드라인**

본 문서는 프로젝트의 코드 품질, 일관성, 유지보수성을 향상시키기 위한 핵심 원칙과 규칙을 정의합니다. 모든 팀원은 아래 가이드라인을 숙지하고 준수해 주시기 바랍니다.

### **I. 기본 원칙 (Core Principles)**

#### **1. 코드의 가독성 및 명료성 (Code Readability & Clarity)**

주석보다 코드로 말합니다. 코드 자체가 의도를 명확히 드러내도록 작성하는 것을 최우선 목표로 삼습니다.

- **자기 서술적 코드 작성**: 명확한 변수명, 함수명, 모듈 구조화를 통해 코드의 목적과 흐름이 자연스럽게 읽히도록 합니다.
- **주석의 제한적 사용**: 주석은 코드로 표현할 수 없는 맥락을 설명할 때만 제한적으로 사용합니다. 예를 들어, 복잡한 비즈니스 로직의 배경, 특정 알고리즘을 선택한 이유, 외부 시스템 연동 시 주의사항 등이 해당됩니다. `// 이 변수는 사용자 이름입니다` 와 같은 명백한 내용은 주석으로 작성하지 않습니다.

#### **2. YAGNI (You Ain't Gonna Need It) 원칙 준수**

현재 요구사항에 명시된 기능만 구현합니다. 이는 프로젝트의 복잡성을 낮추고 유지보수 비용을 절감하는 것을 목표로 합니다.

- **불필요한 기능 구현 지양**: 미래에 필요할 것이라는 예측만으로 현재 요구사항에 없는 기능을 미리 구현하지 않습니다.
- **과도한 추상화 방지**: 당장 필요하지 않은 복잡한 설계나 추상화 레이어를 추가하지 않습니다. 단, 코드의 확장성을 건강하게 고려한 설계는 장려됩니다.

### **II. 기술 스택 및 문법 (Tech Stack & Syntax)**

#### **3. TypeScript의 적극적이고 올바른 활용 (Proactive and Correct Use of TypeScript)**

타입스크립트는 단순한 문법이 아닌, 코드의 안정성을 보장하는 핵심 도구입니다.

- **모든 코드 타입스크립트 작성**: 프로젝트의 모든 새로운 코드는 TypeScript로 작성하는 것을 원칙으로 합니다.
- **`any` 타입 사용 엄격히 금지**: `any` 타입은 타입스크린의 장점을 무력화시키므로 사용을 금지합니다. 외부 라이브러리 연동 등 불가피한 경우에는 `unknown`을 사용한 후, 타입 가드(Type Guard)를 통해 타입을 좁혀나가며 안전하게 사용합니다.
- **타입 정의 및 관리**: 재사용 가능한 인터페이스나 타입은 `types` 디렉토리 또는 관련 도메인 파일 내에 명확하게 정의하여 관리합니다.

#### **4. Svelte 5 Runes 문법 통일 (Unification with Svelte 5 Runes Syntax)**

프로젝트의 상태 관리 로직을 일관되고 현대적인 방식으로 통일합니다.

- **Rune 기반 상태 관리**: 모든 새로운 Svelte 컴포넌트의 상태 관리는 Rune(`$state`, `$derived`, `$effect` 등)을 사용하여 구현합니다.
- **점진적 마이그레이션**: 기존의 `$` 문법으로 작성된 레거시 컴포넌트를 수정할 일이 생길 경우, 해당 컴포넌트를 Rune 문법으로 점진적으로 마이그레이션하는 것을 적극 권장합니다.

#### **5. 일관된 UI/UX를 위한 `shadcn-svelte` 활용 (Leveraging `shadcn-svelte` for Consistent UI/UX)**

UI 컴포넌트의 파편화를 방지하고 프로젝트 전체의 디자인 일관성을 유지합니다.

- **`shadcn-svelte` 컴포넌트 우선 사용**: 새로운 UI 요소를 구현할 때, `shadcn-svelte`에서 제공하는 컴포넌트를 최우선으로 고려하고 활용합니다.
- **컴포넌트 조합(Composition) 고려**: `shadcn-svelte`에 원하는 컴포넌트가 없을 경우, 여러 기본 컴포넌트를 조합하여 구현할 수 있는지 먼저 검토합니다.
- **커스텀 컴포넌트 구현 가이드**: 조합으로 해결할 수 없어 새로운 컴포넌트를 직접 구현해야 한다면, 반드시 `shadcn-svelte`의 디자인 시스템(컬러, 타이포그래피, 간격 등)을 준수하여 프로젝트 전체의 시각적 일관성을 해치지 않도록 합니다.

#### 절대 `pnpm run dev`와 같은 명령어를 실행시키지 말것

- 코드 작성자는 이미 다른 터미널을 통해 현재의 소스코드를 실행시켜보고 있으므로, 절대 중복된 `pnpm run dev`를 동작시키지 말것.

#### 반드시 Cline의 도구를 사용할 것

- 코드 작성자는 `rm` `mv` `ls -l`같은 명령어보다는 MCP 내부의 도구를 활용할 것
